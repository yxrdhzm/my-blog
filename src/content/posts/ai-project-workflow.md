很多人让AI写项目，结果上下文爆炸、代码跑偏、前后矛盾。问题不在AI能力，在**怎么喂任务**。

本文用一个真实流程演示：从零开始，分五层让AI写一个完整项目。每一步都附带可直接复制使用的提示词。

---

## 核心原则：自底向上，分层构建

像盖房子一样——先打地基，再起墙，再装修。不要一上来就让AI写整个项目。

```
第1层：项目脚手架     → 目录结构 + 配置文件 + 依赖声明
第2层：基础设施层     → 通用工具、数据库连接、缓存、对外接口封装
第3层：核心引擎层     → 业务逻辑、算法、数据处理管线
第4层：应用编排层     → 串联各模块、任务调度、导入导出
第5层：展示层         → Web UI / CLI / API 接口
```

每一层**只依赖下层，不依赖上层**。写完一层验证一层，再写下一层。

---

## 阶段门禁：每个阶段之间必须过的检查点

不是写完一步就直接跳下一步。每个阶段之间有一个**门禁**——必须通过才能进入下一阶段。跳过门禁，后面大概率返工。

```
需求文档 ──门禁1──→ 技术架构 ──门禁2──→ 脚手架 ──门禁3──→ 分层实现 ──门禁4──→ 部署
```

| 门禁 | 检查什么 | 不通过怎么办 |
|------|----------|-------------|
| 门禁1：需求→架构 | 需求有没有歧义？边界清不清楚？ | 回去让AI澄清，改需求文档 |
| 门禁2：架构→脚手架 | 选型你同意吗？模块划分合理吗？失败场景考虑到了吗？ | 让AI重新出方案，直到你满意 |
| 门禁3：脚手架→实现 | 目录结构能跑吗？依赖声明完整吗？ | 修脚手架，别在烂基础上盖楼 |
| 门禁4：实现→部署 | 全流程跑通了吗？测试过了吗？边界情况测了吗？ | 回去修代码，别带着问题上线 |

**门禁的执行方式：** 每个门禁就是一轮对话。把当前阶段的产出发给AI，让它帮你审一遍：

```
请审查以下 [需求文档 / 架构文档 / 代码]，检查：

1. 有没有遗漏或矛盾的地方
2. 有没有没考虑到的边界情况
3. 有没有设计不足或过度设计
4. 给出"通过"或"不通过"的结论，不通过列出具体问题
```

## 版本控制：什么时候 commit

不要等全写完再 commit。每个阶段结束时必须 commit，理由很简单：**出了问题能回滚**。

| 时机 | commit message 格式 | 说明 |
|------|---------------------|------|
| 需求文档写完 | `docs: 添加需求文档` | 锁定需求基线 |
| 架构文档写完 | `docs: 添加技术架构文档` | 锁定设计决策 |
| 脚手架搭完 | `chore: 初始化项目脚手架` | 空项目能跑 |
| 每层实现完 | `feat(infra): 实现配置加载和数据库连接` | 带模块前缀 |
| 测试写完 | `test(core): 添加优化器单元测试` | 测试和实现分开 |
| 部署配置完 | `ci: 添加部署配置` | CI/CD 配置 |

**原则：** 每个 commit 都应该是一个**可运行的、可回滚的最小变更**。不要把需求文档和代码放在同一个 commit 里。

## 第0步：需求文档——让AI帮你梳理

你脑子里有想法，但不够结构化。先让AI帮你整理成文档。

### 提示词

```
我有一个想法：[一句话描述你的项目]

请帮我写一份需求文档，包含以下部分：
1. 项目定位：一句话说清楚这是什么
2. 目标用户：谁会用
3. 核心功能（不超过5个）：每个功能用"作为XX，我希望XX，以便XX"的格式
4. 不做的功能：明确排除什么
5. 技术约束：语言/框架/部署方式的偏好（没有就说没有）
6. 参考产品：类似的产品有哪些，你想借鉴什么

不要写实现细节，只写需求。输出为 Markdown 格式。
```

**验证：** 读一遍，把有歧义的地方标出来，追问AI让它澄清。

---

## 第0.5步：技术架构文档——让AI帮你选型

需求文档告诉你"要做什么"，架构文档告诉你"怎么做"。这一步让AI帮你做技术选型和模块设计。

**为什么单独一步：** 如果跳过直接写脚手架，AI会自己选技术方案，选出来的可能不适合你。你要先拍板。

### 提示词

```
根据以下需求文档，输出一份技术架构文档：

需求文档：[粘贴需求文档]

请按以下结构输出：

1. 技术选型（每个给出2-3个候选，说明优劣，给出推荐）
   - 编程语言：
   - Web框架：
   - 数据库：
   - 包管理：
   - 测试框架：
   - 部署方式：

2. 系统架构
   - 分层方式：[推荐分层并说明理由]
   - 模块划分：[每个模块的职责和边界]
   - 模块依赖关系：[谁依赖谁，画出依赖图]

3. 数据模型
   - 核心实体：[列出主要数据对象]
   - 实体关系：[1对1 / 1对多 / 多对多]

4. 接口设计
   - 模块间通信方式：[函数调用 / 消息队列 / API]
   - 关键接口签名：[列出核心函数的输入输出]

5. 目录结构预览
   - 基于模块划分给出建议的目录结构

6. 失败场景设计
   - 每个模块可能的失败原因：[网络超时、API限流、数据格式错误...]
   - 失败后的处理策略：[重试 / 降级 / 报错退出]
   - 关键的重试策略：[重试次数、退避方式]

注意：
- 给出推荐方案，但列出替代选项让我选择
- 不要写实现代码，只做设计决策
- 如果某个选型取决于项目规模，说明适用场景
```

### 你来做的关键决策

AI会给你几个选项，你需要拍板：

| 决策点 | AI会问你 | 怎么选 |
|--------|----------|--------|
| 语言/框架 | React还是Vue？FastAPI还是Django？ | 选你熟的，或选AI更擅长生成代码的 |
| 数据库 | PostgreSQL还是SQLite？ | 小项目SQLite够用，要扩展就PostgreSQL |
| 部署方式 | Docker还是Serverless？ | 个人项目Serverless省心，企业项目Docker |
| 分层方式 | 几层？每层叫什么？ | 按职责分，不超过5层 |

**验证：** 把架构文档存到 `docs/architecture.md`。后续每一步提示词都引用这个文件。

## 第1步：项目脚手架

脚手架的作用是**定规矩**——目录结构、编码规范、依赖版本。AI后续写代码都在这个框架里，不会乱放文件。

### 提示词

```
根据以下技术架构文档，生成项目脚手架：

技术栈：
- 语言：Python 3.11+
- 包管理：uv
- 测试：pytest
- 代码风格：ruff

请生成：
1. 目录结构（tree 格式）
2. pyproject.toml（包含项目元信息、依赖、工具配置）
3. 每个目录下的 __init__.py
4. 一个最小的 main.py 入口
5. .gitignore
6. README.md（简要说明项目是什么、怎么跑）

技术架构文档：[粘贴 docs/architecture.md]

注意：不要写业务逻辑代码，只搭骨架。
```

### 这一步的产出示例

```
my-project/
├── pyproject.toml
├── README.md
├── .gitignore
├── src/
│   ├── __init__.py
│   ├── main.py
│   ├── core/          # 核心引擎
│   │   └── __init__.py
│   ├── infra/         # 基础设施
│   │   └── __init__.py
│   ├── app/           # 应用编排
│   │   └── __init__.py
│   └── ui/            # 展示层
│       └── __init__.py
└── tests/
    └── __init__.py
```

**验证：** `uv sync` 能跑通，`uv run python -m src.main` 不报错。

## 第2步：基础设施层

这层写的是**所有模块都会用到的东西**：数据库连接、配置加载、日志、外部API封装。这层没有业务逻辑，纯粹是"工具箱"。

### 提示词

```
项目脚手架已就绪，现在实现基础设施层（src/infra/）。

需要实现的模块：

1. config.py — 配置加载
   - 从环境变量和 .env 文件读取配置
   - 用 dataclass 或 pydantic 定义配置结构
   - 包含数据库URL、API密钥、日志级别等

2. database.py — 数据库连接
   - 使用 SQLAlchemy async
   - 提供 get_session 依赖注入函数
   - 包含 Base 和 init_db 函数

3. cache.py — 缓存层
   - 支持内存缓存（简单场景）和 Redis（可选）
   - 统一接口：get / set / delete

4. llm_client.py — LLM 调用封装
   - 封装 Anthropic/OpenAI SDK
   - 统一接口：chat(messages, **kwargs) → str
   - 支持重试、超时、流式输出

已有文件：
- src/infra/__init__.py
- pyproject.toml（依赖已声明）

要求：
- 每个模块独立可测试
- 只用已声明的依赖，不要引入新包
- 写完后在 tests/infra/ 下写对应的单元测试
```

**验证：** `pytest tests/infra/` 全部通过。用一个小脚本测试数据库连接和LLM调用是否正常。

---

## 第3步：核心引擎层

业务逻辑写在这里。这是项目最核心的部分，**依赖基础设施层，不依赖上层**。

### 提示词

```
基础设施层已完成（src/infra/），现在实现核心引擎（src/core/）。

核心引擎包含：

1. optimizer.py — 优化器
   - 输入：一组候选方案 + 评估结果
   - 输出：根据反馈生成新的候选方案
   - 使用 src/infra/llm_client.py 调用 LLM

2. evaluator.py — 评估器
   - 输入：一个方案
   - 输出：评分 + 评语
   - 可扩展：支持多种评估维度

3. pipeline.py — 管线
   - 串联 optimizer 和 evaluator
   - 实现迭代循环：生成 → 评估 → 反馈 → 再生成
   - 支持配置最大迭代次数

4. schema.py — 数据模型
   - 用 dataclass 定义 Solution、EvaluationResult 等核心类型
   - 所有模块共享这些类型

已实现的基础设施：
- src/infra/config.py：get_config() 获取配置
- src/infra/llm_client.py：LLMClient.chat() 调用LLM
- src/infra/cache.py：Cache.get/set 缓存

要求：
- 所有模块只依赖 src/infra/ 和 src/core/schema.py
- 不要直接 import 环境变量，通过 config 模块读取
- 写完后在 tests/core/ 下写单元测试（mock LLM 调用）
```

**验证：** `pytest tests/core/` 全部通过。手动跑一次 pipeline，确认能走通一个最小迭代。

---

## 第4步：应用编排层

这层负责**串联引擎和外部世界**：读取输入、调度引擎、导出结果。

### 提示词

```
核心引擎已完成（src/core/），现在实现应用编排层（src/app/）。

需要实现：

1. runner.py — 任务运行器
   - 读取用户输入（配置/参数）
   - 初始化 pipeline
   - 运行完整流程并返回结果
   - 支持中断和恢复

2. exporter.py — 结果导出
   - 支持导出为 JSON / Markdown / CSV
   - 输出到文件或标准输出

3. cli.py — 命令行入口
   - 使用 click 或 argparse
   - 命令：run（执行任务）、export（导出结果）、list（列出历史）

已实现的核心引擎：
- src/core/pipeline.py：Pipeline.run(iterations=N) 运行管线
- src/core/schema.py：所有数据类型
- src/infra/config.py：get_config() 获取配置

要求：
- runner 是胶水层，不要在这里写业务逻辑
- cli.py 是最薄的一层，只做参数解析和调用 runner
- 写完后在 tests/app/ 下写测试
```

**验证：** `uv run python -m src.app.cli run --config config.yaml` 能跑通。导出的文件格式正确。

---

## 第5步：展示层

最后一层才是UI。因为底层都写好了，UI层只需要调用 app 层的接口。

### 提示词

```
所有底层模块已完成，现在实现 Streamlit UI（src/ui/）。

UI 需要包含以下页面：

1. 主页 — 任务配置
   - 表单：输入参数、选择模式、配置迭代次数
   - "开始运行"按钮

2. 运行页 — 实时展示进度
   - 显示当前迭代轮次
   - 显示最新评估结果
   - 支持中途停止

3. 结果页 — 展示和导出
   - 表格展示所有方案和评分
   - 支持按评分排序
   - 一键导出为 JSON / Markdown

已实现的底层接口：
- src/app/runner.py：Runner.run(config) → Result
- src/app/exporter.py：Exporter.export(result, format, path)
- src/core/schema.py：Solution、EvaluationResult 等类型

要求：
- UI 层只调用 src/app/ 的接口，不直接调用 core 或 infra
- 用 session_state 管理状态
- 放在 src/ui/app.py，用 streamlit run src/ui/app.py 启动
```

**验证：** 启动 Streamlit，走一遍完整流程：配置 → 运行 → 查看结果 → 导出。

## 第6步：部署——让项目能被别人用

代码写完不叫完成，**跑在服务器上、别人能访问到**才叫完成。

### 提示词

```
项目已完成，现在配置部署。

项目信息：
- 技术栈：[Python + Streamlit / FastAPI / ...]
- 运行方式：[uv run / docker]
- 需要的环境变量：[列出]

请生成以下文件：

1. Dockerfile
   - 基础镜像选择（考虑安全性和体积）
   - 多阶段构建（构建阶段 + 运行阶段）
   - 非 root 用户运行
   - 健康检查配置

2. docker-compose.yml（如果需要多个服务）
   - 应用服务
   - 数据库服务（如果需要）
   - 环境变量配置
   - 数据持久化挂载

3. .env.example
   - 列出所有需要的环境变量和示例值
   - 不包含真实密钥

4. 部署文档（docs/deployment.md）
   - 本地开发怎么跑
   - 生产环境怎么部署
   - 常见问题排查

5. GitHub Actions（如果部署到云平台）
   - 自动构建和部署
   - 测试在部署前运行

要求：
- 不要在镜像里硬编码密钥
- .env 文件不进 git（已在 .gitignore）
- 暴露必要端口，其他端口不开放
```

**验证：**
1. `docker build -t my-app .` 构建成功
2. `docker run --env-file .env.example -p 8080:8080 my-app` 能正常启动
3. 用浏览器访问 `localhost:8080`，核心流程能走通

## 上下文管理：防止AI跑偏的技巧

写项目过程中，AI最大的问题是**上下文越写越长，开始"忘记"之前的约定**。

### 技巧1：维护一个约定文件

在项目根目录创建 `docs/conventions.md`，每次让AI写新模块前，先让它读这个文件。

```
在写代码前，先读 docs/conventions.md，遵循里面的编码规范和架构约定。
然后完成以下任务：[具体任务]
```

`conventions.md` 长这样：

```markdown
# 编码约定

## 架构
- src/infra/：基础设施，不含业务逻辑
- src/core/：核心引擎，只依赖 infra
- src/app/：编排层，串联 core 和 infra
- src/ui/：展示层，只调用 app 层接口

## 代码风格
- 类型标注：所有函数必须有完整类型标注
- 异步优先：IO 操作用 async/await
- 错误处理：业务异常用自定义 Exception，不用裸 except

## 依赖规则
- 禁止跨层 import（core 不能 import app）
- 新依赖必须加到 pyproject.toml 并说明理由
```

### 技巧2：新模块开新对话

写完一个模块后，开一个新对话。在新对话开头：

```
我正在开发一个 [项目名]，技术栈是 [XX]。

项目目录结构：
[粘贴 tree 输出]

当前已完成的模块：
- src/infra/config.py：配置加载
- src/infra/llm_client.py：LLM调用封装
- ...

现在需要实现：[新任务]

相关文件的接口定义：
[粘贴关键接口代码]
```

这比让AI在长对话里继续写要可靠得多。

### 技巧3：用接口文件锁定模块边界

让AI在每个模块写完后，自动生成一个 `interface.py`，只包含类型定义和函数签名：

```
为 src/core/ 模块生成一个 interface.py，只包含：
1. 所有公开类的定义（dataclass）
2. 所有公开函数的签名（参数类型 + 返回类型）
3. 不包含任何实现代码

后续模块只依赖这个 interface.py，不直接 import 具体实现。
```

后续模块写代码时，给AI的上下文只需要这个 `interface.py`，不需要整个模块的实现细节。

## 完整流程速查

| 步骤 | 做什么 | 产出 | 验证 | 门禁 |
|------|--------|------|------|------|
| 第0步 | 需求梳理 | 需求文档 | 自审歧义 | 门禁1：需求无歧义 |
| 第0.5步 | 技术架构 | 架构文档 + 失败场景 | 存到 docs/ | 门禁2：选型你同意 |
| 第1步 | 项目脚手架 | 目录结构 + 配置 | 能跑空项目 | 门禁3：项目能跑 |
| 第2步 | 基础设施层 | 工具模块 + 测试 | 单测通过 | — |
| 第3步 | 核心引擎层 | 业务逻辑 + 测试 | 单测通过 | — |
| 第4步 | 应用编排层 | CLI + 导出 + 测试 | 命令行跑通 | — |
| 第5步 | 展示层 | Web UI | 端到端走通 | 门禁4：全流程通过 |
| 第6步 | 部署 | Docker + CI/CD | 服务器能访问 | — |

## 进阶技巧

基础流程能跑通项目，但如果你想**写得更快、质量更高**，下面四个技巧能显著提升效果。

---

### 技巧A：TDD驱动——先写测试，再写实现

常规做法是先写代码再补测试。反过来更好——先让AI写测试，再让它实现。测试就是验收标准，AI有了明确目标，不容易跑偏。

**为什么有效：**
- 测试定义了"什么算完成"，AI不会过度设计
- 写完就能跑，立刻知道对不对
- 测试本身就是文档，描述了模块的预期行为

**流程：**

```
第1轮：让AI写测试
第2轮：让AI看测试，写实现让它通过
验证：pytest 全绿
```

**提示词——第1轮：写测试**

```
项目目录结构：[粘贴 tree]

现在要实现 src/core/optimizer.py，功能是：[一句话描述]

在写实现之前，先在 tests/core/test_optimizer.py 写单元测试，覆盖：
1. 正常输入 → 正常输出
2. 边界情况：空输入、单条输入、超长输入
3. 异常情况：无效参数 → 抛出明确异常

要求：
- 使用 pytest + pytest-asyncio
- mock 所有外部依赖（LLM调用、数据库）
- 测试用例要能独立运行，不依赖真实服务
- 先不写实现，只写测试（会故意失败）
```

**提示词——第2轮：写实现**

```
tests/core/test_optimizer.py 已写好，当前全部失败。

阅读测试文件，理解预期行为，然后实现 src/core/optimizer.py 使其通过所有测试。

要求：
- 不要修改测试文件
- 实现必须通过全部测试用例
- 通过后运行 pytest tests/core/test_optimizer.py 确认全绿
```

**验证：** `pytest tests/core/test_optimizer.py` 全部通过。如果AI修改了测试来"适配"实现，推倒重来。

### 技巧B：Spike先行——先写草稿，再写生产代码

遇到不确定怎么实现的功能，别直接让AI写"生产级代码"。先让它写一个粗糙原型验证思路，再让它基于原型重写。

**为什么有效：**
- 原型探索成本低，错了不心疼
- 写过一遍再写第二遍，质量远高于直接写
- 你能先看到效果再决定方向

**流程：**

```
第1轮：写Spike（粗糙原型）
第2轮：验证思路可行
第3轮：基于Spike重写成生产代码
```

**提示词——第1轮：写Spike**

```
我想实现 [功能描述]，但不确定最佳方案。

请写一个 spike（粗糙原型），验证以下思路是否可行：
[你想到的实现思路]

要求：
- 放在 spike/ 目录
- 不考虑错误处理、性能、代码风格
- 能跑通一个最小示例就行
- 写完后跑一遍，告诉我结果
```

**提示词——第3轮：基于Spike重写**

```
spike/prototype.py 是一个验证思路的粗糙原型。

现在基于这个原型，在 src/core/ 下写生产级实现：

1. 保留核心算法逻辑
2. 补充完整的错误处理
3. 添加类型标注
4. 重构为项目规范的模块结构
5. 写对应的测试

原型代码：[粘贴 prototype.py]

要求：
- 不要照搬原型的结构，按项目架构重新组织
- 通过 tests/core/ 下的测试
```

**验证：** 原型能跑通 → 重写后的代码能跑通 → 测试全绿。

### 技巧C：多角色对话——让AI自己审自己

单一视角容易有盲区。开多个对话窗口，给AI不同的角色，让它互相审查。

**为什么有效：**
- "架构师"会发现"程序员"忽略的设计问题
- "安全审查员"会发现"开发者"忽略的漏洞
- 不同视角能覆盖更多问题

**三个角色：**

| 角色 | 对话窗口 | 职责 |
|------|----------|------|
| 架构师 | 窗口A | 审需求、审设计、审代码结构 |
| 开发者 | 窗口B | 写代码、写测试、做实现 |
| 审查员 | 窗口C | code review、找bug、找安全问题 |

**提示词——窗口A：架构师角色**

```
你是一个资深架构师，负责审查设计和代码质量。

项目背景：[简要描述]

请审查以下模块的设计：
[粘贴代码或设计文档]

审查维度：
1. 模块职责是否单一
2. 依赖方向是否正确（上层依赖下层，不反向）
3. 接口设计是否合理
4. 有没有过度设计或设计不足

输出格式：问题列表 + 修改建议，按严重程度排序。
```

**提示词——窗口C：审查员角色**

```
你是一个严格的代码审查员，专门找bug和安全问题。

请审查以下代码：
[粘贴代码]

审查维度：
1. 逻辑错误和边界条件
2. 安全漏洞（注入、越权、敏感信息泄露）
3. 性能隐患
4. 异常处理是否完善

输出格式：每个问题标注文件、行号、严重程度（高/中/低）、修复建议。
```

**工作流：**

```
1. 开发者窗口写完代码
2. 架构师窗口审查设计 → 反馈给开发者修改
3. 审查员窗口审查代码 → 反馈给开发者修改
4. 开发者窗口修改后，再过一遍审查
5. 两边都满意了，再进下一步
```

### 技巧D：代码审查循环——写完就审，审完就改

不用多角色那么复杂，最简单的版本：写完一个模块，新开对话让AI review，发现问题再修。

**为什么有效：**
- AI审AI的代码，能发现"写的时候没想到"的问题
- 新对话没有上下文包袱，审查更客观
- 成本很低，每次就多一轮对话

**提示词——审查**

```
请审查以下代码，找出问题：

文件：src/core/pipeline.py
[粘贴代码]

审查标准：
1. 逻辑是否正确
2. 错误处理是否完善
3. 有没有更简洁的写法
4. 类型标注是否完整

按严重程度排序输出，给出具体的修改建议。
```

**提示词——修复**

```
根据以下审查意见，修复 src/core/pipeline.py：

审查意见：[粘贴审查结果]

要求：
- 只修复审查指出的问题
- 不要做额外的"改进"
- 修复后跑一遍测试确认没有引入新问题
```

**流程：** 写代码 → 新对话审查 → 修改 → 再审查 → 通过后进下一步。通常两轮审查就能达到不错的质量。

---

## 总结

让AI写项目的关键不是"AI有多强"，而是**你能不能把任务拆到AI能可靠执行的粒度**。

基础纪律：
1. **一次一层**，不要跳步
2. **写完验证**，不要攒到最后
3. **上下文隔离**，新模块开新对话

流程纪律：
4. **阶段门禁**——每个阶段之间必须审查，通过才进下一步
5. **版本控制**——每个阶段结束 commit，出问题能回滚
6. **失败设计**——架构阶段就考虑失败场景，别等出了问题再补

进阶技巧：
7. **TDD驱动**——测试先行，AI目标明确
8. **Spike先行**——先探索再生产，降低返工成本
9. **审查循环**——写完就审，用另一个视角兜底

AI是执行者，你是架构师和质量经理。流程设计得好，产出就不会差。
